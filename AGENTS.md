# AGENTS.md — dsh-tool-retry (tool-call checkpoint & replay)

Rules for the dsh-tool-retry plugin: automatic checkpointing of every model-direct tool-call block (success or failure), a minimal post-failure notification, and a replay path that lets the model edit a saved call's arguments instead of regenerating them.

**This plugin lives OUTSIDE the harness checkout** — it is developed in this repo and loaded into a DSH profile through a development alias plus a user-authored agent preset, with zero modifications to the deepseek-harness source tree. The authoritative design is [docs/tool-calling-checkpoint-replay-plan.md](docs/tool-calling-checkpoint-replay-plan.md) (this repo). Before touching services, events, or prompt sections, read <harness>/packages/AGENTS.md, <harness>/AGENTS.md, and the code-map references in the plan's appendix. Resolve the active harness root with scripts/harness-path.ts (or DSH_HARNESS); relative links to an assumed sibling checkout are forbidden.

## Loading model (why development uses a profile-local package alias)

- Agent-plane plugins (tools + tools/post-execute listeners) are composed per session from an **agent preset**. The shipped presets live inside the harness checkout and must not be edited; the sanctioned external channel is the user preset root: ~/.dsh/.agent-presets/<id>/agent.cordis.yml. This repo ships two preset templates (tool-retry-standard and tool-retry-code) that copy the shipped standard/code presets and add one row - id: tool-retry / name: '<entry>'.
- Development resolves <entry> through the profile-local alias @dsh-tool-retry-dev/plugin: scripts/profile-plugin-link.ts creates or repairs exactly one symlink at $DSH_HOME/profiles/<profile>/node_modules/@dsh-tool-retry-dev/plugin pointing to packages/dsh-tool-retry. A non-symlink at that alias is never replaced.
- The launch overlay (cordis.yml, generated by pnpm gen-config) inserts one row naming the dev alias. The tsdown banner id must equal the entry name; scripts/development-entry.ts is the single source.
- **Official publication is separate from the dev channel.** pnpm package:official stages a prebuilt tarball whose manifest declares dsh.bundle.patch (cordis.patch.yml with - insert: of @canglongcl/dsh-tool-retry). Bundle patches apply to the profile graph; the agent plane still needs the user preset row naming the installed official package. The generated dist/package/ allowlist is exact — source, .git, node_modules, and dev-link state must never enter the official package.
- The built node half must stay self-contained: no runtime node_modules dependency; small DSH construction helpers (createUserMessage, CallId) must be inlined by tsdown, never a surviving bare runtime import.

## Core design invariants

### Checkpoint scope and content

- **Model-direct calls only**: exec.parent === undefined. Native mode checkpoints every tool call; PTC (code) mode checkpoints only the run_code call — the whole program parameter. Sub-dispatches inside a program, **including nested run_code**, are never checkpointed.
- **Zero filtering (store) / byte-gated notices**: every model-direct call that reaches tools/post-execute is CHECKPOINTED regardless of tool name or error code (UNKNOWN_TOOL, INVALID_ARGS included), but the failure NOTICE fires only when the call's raw argument string is `NOTICE_MIN_ARG_BYTES` (150) UTF-8 bytes or more — below it a fresh re-send is cheaper than the replay call's routing structure, so the hint would be a net loss. `editPreviousToolCalling`'s own failures are exempt from the gate (their notice carries the original-call retry pointer, which is corrective, not economic). This is safe because alias re-pointing happens in tools/post-execute — after the tool body ran. Verified registry boundary (tools/src/index.ts): a call cancelled at entry takes the `final-result` stage, which BYPASSES tools/post-execute — ABORTED_BEFORE_DISPATCH can never be checkpointed or notified; a post-body ABORTED still checkpoints (the waterfall saw the call) but its result replacement happens after our decision, so that failure gets no notice. Both are documented limits, not bugs.
- **Content is the raw argument string** taken from the session tool/call event by callId — byte-identical to what the model sent. Never wrap it. Invalid-JSON raw strings are stored verbatim.

### Storage layout

- Root: <os.tmpdir()>/.dsh/tool-checkpoints/<sessionId>/ (never session.header.cwd).
- by-id/<sanitize(id)>.json — the **only real store**, one file per call, never overwritten for the session. sanitize = non-[A-Za-z0-9._-] → _.
- previous/1.json, previous/2.json … — symlinks (or Windows copy fallback) to the by-id files of the previous message's parallel blocks, in model order. Rebuilt each round: on the first model-direct call of a new (turn, step) (at its post-execute, after the tool body), delete all previous aliases, then create one per committed call.
- history.jsonl — append one index line per call: { id, tool, turn, step, ordinal }.
- Round order = **commit order = model order** (commitReady, tool-calls.ts:146-160); parallel bodies may overlap but numbering never depends on execution overlap.

### Alias mechanics

- Use fs.symlink; on EPERM (Windows without Developer Mode/admin) fall back to writing a copy (content-equal, also fs/observed-registered). Never hardlink (atomic rename writes diverge) and never .lnk (Node fs does not follow it). Non-local fs backends (e2b) skip aliases silently; notifications still carry exact paths.
- Each alias replacement is atomic (temp name + rename).

### fs observation bypass (edit without read)

- After every ctx.fs.writeText, synchronously ctx.emit('fs/observed', target, { kind: 'present', version: outcome.version }, exec). Use the **write outcome's version** (never a fresh stat); the actor must be the call's exec (undefined records nothing). resolve follows the symlink to the same targetKey, so edits through previous/n.json satisfy the observation policy.

### Failure notification

- Hook: tools/post-execute waterfall. Always await next(); on result.isError === true attach one createUserMessage to the decision's additionalContexts with source { kind: 'plugin', plugin: '@canglongcl/dsh-tool-retry', form: 'notice' }.
- **Minimal body**: "saved" + call id (+ by-id path in PTC) + how to use it. Never repeat the failure reason — the harness tool/result already carries it. No throttling, no truncation logic.
- If the checkpoint write fails (sandbox read-only, backend error): log, skip the notification, and never block the pipeline.

### Replay tool (native only)

- editPreviousToolCalling({ previous_ordinal?, call_id?, patch }) — exactly one of previous_ordinal (number) / call_id (string); both or neither is an error. `patch` is the ONLY edit payload (required, non-empty): entries `{ path, value? | old_string?, new_string?, replace_all? }` — `value` replaces the whole value at the path (any JSON type; omit value AND old/new to delete the field, array indexes splice); `old_string/new_string` applies a literal replace inside the string value at the path, matched against its DECODED text (no JSON escaping enters the model's view), `replace_all` defaults false and duplicate matches error with the count. Paths are dot segments + `[n]` indexes from the checkpoint's top-level keys; a missing path errors with the key list.
- Routing: previous_ordinal → in-memory round map → the call's **by-id file**; call_id → sanitized by-id/<call_id>.json. Always edit the by-id file directly (aliases serve fs-tool paths only). Path containment: resolved target must stay inside this session's checkpoint dir.
- Ordinal stability: previous_ordinal means "the PREVIOUS message's calls", but the round map re-points at the first direct call of each message — so a replay call that is not the message's first call (a parallel sibling, or after an earlier call like a read) resolves against the current message's map. The tool detects that (resolved entry shares the replay call's own (turn, step)) and rebuilds the map from the session log with the current message's group excluded; the guidance text also tells the model to prefer call_id in that situation.
- Edit path, with a resume guard first: the observation table is in-memory and does NOT survive a restart, so the tool re-writes the by-id file's current content through ctx.fs and re-emits fs/observed (the plugin's own write-then-emit pattern); then readText → JSON.parse (failure = explicit error) → apply the patch entries in order → persist JSON.stringify(patched) (no trailing newline, matching the checkpoint format) → nested replay.
- Nested replay: ctx.tools.execute({ callId: CallId('<orig>:replay'), name, arguments, agent: exec.agent, rootCallId: exec.rootCallId, parent: exec.token, signal: exec.signal }). parent: exec.token marks it a sub-dispatch (no re-checkpoint, no notification, full pre/execute/post/result pipeline, approval re-applies).
- Registration condition: register only when ctx.tools.get(RUN_CODE_NAME, agent) === undefined || ctx.get('codeRuntime') === undefined (dual detection; the reserved name cannot be forged — register() rejects it unconditionally, index.ts:1053-1055). The tool is exclusive (no isConcurrencySafe).

### Mode detection and prompt governance

- Code-mode detection is the dual condition above; native/code/both need no distinction beyond it (run_code visible + runtime loaded → treat as code).
- Static section tool:checkpoint-replay order 149 (mode-conditional text via AssembleContext.scope): the checkpoint layout plus THREE XML-shaped retry examples (plan rejected — fix one section of the long plan string; edit rejected a stale fragment — patch the saved call's own .old_string; wrong type — replace the whole value). There is NO separate guidance section: the usage rules live in the tool's own description (single source). The reviewed drafts live in the plan's appendix B; Chinese translations there are review aids only — injection language stays English until review says otherwise.
- The model never computes ids or paths: ids are injected verbatim and echoed back; usage matrix = previous message → ordinal, older → call id (failed: injected; successful: tail history.jsonl).

### Lifecycle

- Per-session in-memory round map; on process restart rebuild it from the session log's last tool/call step tail (by-id files and history.jsonl are on disk). The rebuild is LAZY: it also runs inside the replay tool when the first previous_ordinal lookup misses, so the first ordinal replay after a restart/resume resolves instead of failing (the round-map rebuild at post-execute runs after the tool body).
- Cleanup: session/disposed removes the session directory; ctx.effect teardown is the HMR backstop.

## Known limitations (do not "fix" into breakage)

- Windows copy fallback: edits through an alias diverge from the by-id file (native replay edits by-id directly, so only PTC fs-tool edits are affected; self-consistent).
- os.tmpdir() may be reclaimed by the OS between sessions; within a session the plugin recreates directories as needed.
- both mode is treated as code mode (public API cannot distinguish): editPreviousToolCalling is not registered there.
- PTC retry guidance is loader-based (resolved from the plan's decision 10): the model reads the checkpoint, JSON.parses it, applies a literal replace on the real program text (`prev.code`), then runs the corrected program through the `AsyncFunction` constructor (`new AsyncFunction("tools", "console", ...)`) and returns its value — no JSON escaping enters the match, and the corrected program's top-level `return`/`await` keep their native run_code semantics (verified: plain `eval` rejects `return` in strict mode with `SyntaxError: Illegal return statement`, so the guidance must not use eval). The cost: when this retry itself fails, the new checkpoint holds the loader rather than the executed program — the `file_path` inside it still points at the original program, and the guidance says so.
- Replaying an UNKNOWN_TOOL checkpoint fails again (expected; the model moves on).
- No new session event type for replay audit in v1: the replay outcome rides editPreviousToolCalling's own tool/result content and meta.

## Installing the prebuilt tarball into a running profile (official channel)

When a profile should load the plugin through the standard `dsh plugin` path
(the way `dsh plugin --profile web add @canglongcl/dsh-web-review` installs an
npm bundle) rather than the dev alias, stage and install the local tarball:

1. `pnpm package:official` — regenerates `dist/canglongcl-dsh-tool-retry-<version>.tgz`
   (prebuilt lib + cordis.patch.yml declaring `dsh.bundle.patch`).
2. `dsh plugin --profile web add file:$PWD/dist/canglongcl-dsh-tool-retry-<version>.tgz`
   — pnpm-adds the tarball into `$DSH_HOME/profiles/<profile>` and, because the
   manifest declares `dsh.bundle.patch`, auto-registers the package in the
   profile's `dsh.profile.bundles`; at boot the bundle layer's cordis.patch.yml
   inserts the tool-retry row into the host composition.
3. `pnpm install-presets --official` — rewrites the user-preset rows
   (`~/.dsh/.agent-presets/tool-retry-standard` and `tool-retry-code`) to name
   the installed official package instead of the dev alias.
4. Restart the web instance (`dsh web`): bundles compose at boot, so a restart
   is required; sessions persist and resume. The profile manifest must not mix
   the official package with the dev alias — materializeProfilePluginLink
   refuses that combination.
